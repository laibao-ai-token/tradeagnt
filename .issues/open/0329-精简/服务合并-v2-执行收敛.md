# 服务合并执行收敛计划 V2

> 原始方案保留在 `./服务合并.md`。本文件不覆盖原方案，目标是把当前讨论收敛成“在现有仓库约束下可执行”的版本，避免误删、误迁移和越权改动。

> **For agentic workers:** 本文件是执行前的收敛版计划，不是最终逐步实现清单。进入实现前，应基于本文件再展开成更细的 `writing-plans` 任务，并使用 multi-agent 按目录边界并行推进。

**Goal:** 在不破坏现有服务入口、不默认修改数据库 schema、不提前废弃旧目录的前提下，为 `data-service + markets-service + tui-service 基金链路` 建立兼容式合并路径。

**Architecture:** 采用 `compatibility-first` 策略。先冻结范围、边界、读模型和兼容约束，再分阶段引入统一采集入口；所有高风险动作都放到显式 decision gate 之后，并要求双跑、回退和验收口径。

**Tech Stack:** Python 3.12, TimescaleDB, SQLite, shell scripts, existing microservices under `services/` and `services-preview/`

---

## 1. 本文件解决什么问题

当前 `服务合并.md` 的方向基本合理，但还混合了三类内容：

1. 架构目标
2. 实施计划
3. 高风险 cutover 动作

这会带来三个直接问题：

1. 文档里已经包含默认不允许的动作，例如 schema 变更、旧目录废弃、默认启动语义变化。
2. 文档对真实代码的依赖关系写浅了，特别是基金链路、crypto 行为语义、`markets-service` 的 `core/storage/providers/models` 结构。
3. 任务颗粒度过大，不能直接作为 execution-grade `writing-plans` 去跑。

因此，本文件先做范围收敛，再定义后续实现顺序。

---

## 2. 本轮范围（In Scope）

本轮允许进入实现准备的事项只有以下几类：

1. 明确并冻结目标目录契约。
2. 明确并冻结配置兼容策略。
3. 明确基金链路的读模型、symbol 规范和验证矩阵。
4. 将合并路径拆成兼容式阶段，而不是一次性替换。
5. 为每个阶段定义灰度、回滚、验收口径。

本轮优先级按以下顺序执行：

1. 基金链路专项收敛
2. collector 目录与配置契约冻结
3. 共享存储和基础设施迁移规划
4. crypto / equity / news 分片迁移规划
5. 可选 cleanup 规划

---

## 3. 本轮明确不做（Out of Scope）

以下事项不进入当前默认执行主线：

1. 不修改 `config/.env`
2. 不默认执行任何数据库 schema 变更
3. 不创建基金新表、`hypertable`、压缩策略，除非单独批准
4. 不把 `data-service` / `markets-service` 迁到 `_deprecated/`
5. 不修改 `.gitignore`
6. 不移除现有 `./scripts/start.sh start|stop|status|run` 的默认语义
7. 不直接删除 `tui-service` 里的基金直连抓取逻辑
8. 不在未完成双跑验证前切换默认基金数据来源
9. 不在未冻结目录契约前创建大体量 `collector-service` 骨架

---

## 4. 必须先锁定的仓库约束

以下约束在执行任何落地工作前视为硬约束：

1. `config/.env` 只读，不作为迁移期间的修改目标。
2. 数据库 schema 默认只读，任何 DDL 都必须单独审批。
3. 旧服务目录在兼容阶段仍被视为有效入口，不得提前废弃。
4. 顶层脚本、README、AGENTS 中已有的命令和服务拓扑属于外部契约。
5. 所有高风险迁移必须支持灰度运行和回退。

## 5. 关键现实差异

### 5.1 collector 目标结构当前并未冻结

原方案前半段只定义了 `collectors/adapters/utils`，但实际迁移任务已经依赖：

1. `core/`
2. `storage/`
3. `schema_adapter.py`
4. `models/`
5. `providers/`

这意味着“先创建 collector-service 骨架”之前，必须先冻结最终目录契约，否则后续 task 会不断反向修正文档。

### 5.2 markets-service 不是纯股票/新闻服务

真实代码已经吸收了大量 crypto 采集能力，包括：

1. `crypto-backfill`
2. `crypto-metrics`
3. `crypto-ws`
4. `crypto-book-depth`
5. `crypto-order-book`

所以当前工作不是“从 0 合并 data + markets”，而是“在已有 partial merge 现实上继续收敛”。

### 5.3 data-service 的运行语义不止是几个采集脚本

真实行为中至少包含：

1. `.env` 权限校验
2. `SYMBOLS_*` 解析与校验
3. 代理可用性检查
4. `ws` 启动补齐与 gap 巡检
5. `gate_spot` 备用源
6. `backfill` 独立进程语义

因此迁移时必须保留“运行语义”，而不是只复制模块文件。

### 5.4 基金链路不是简单的 quote fetch

当前 TUI 基金页实际包含：

1. `fund_cn` 独立轮询器
2. 场内 / 场外分流抓取
3. 动态候选池和自选变更
4. 运行期 live curve
5. 场内基金 15D 日线补图
6. ETF 排名与 micro snapshot
7. `signal_history.db` 信号叠加

因此 Batch 5 和 Task 6.3 需要先补“基金读模型”，而不是直接写成“改为读 TimescaleDB”。

## 6. 先决 Decision Gates

### Gate A: 是否允许 schema 变更

结论未明确前，默认答案为“否”。

若结论为“否”：

1. 本轮只允许做代码结构预留
2. 基金链路只允许设计读模型和兼容层
3. 不写 DDL，不切默认数据源

若结论为“是”：

1. 单独开 schema 子 issue
2. 单独评审 DDL、索引、压缩策略、回滚方案
3. schema 变更不与业务迁移混在同一批次执行

### Gate B: 基金排名和 micro snapshot 的归属

必须在以下两种方案中二选一：

1. 继续保留在 TUI，本轮只更换底层数据读取方式
2. 上移到服务端生成读模型，TUI 只负责展示

未决前，默认选项为“继续保留在 TUI”。

### Gate C: 订单簿是否纳入本轮

当前文档已把订单簿纳入 collector 范围，但执行复杂度明显更高。

未决前，默认答案为“否”，即：

1. 本轮先不迁移 `book_depth` / `order_book`
2. 先完成 `ws / metrics / backfill` 的兼容收敛
3. 订单簿作为后续独立切片

### Gate D: 是否允许切换默认启动语义

未完成灰度前，默认答案为“否”。

即：

1. 根脚本现有 `start|stop|status|run` 语义不变
2. 即使引入 `collector-service`，也必须先以显式新命令或兼容别名进入
3. 默认语义切换只能发生在 cleanup 阶段

## 7. 目标目录契约（冻结版）

在进入实现前，collector 目标结构至少应冻结到以下级别：

```text
services/collector-service/
├── src/
│   ├── __main__.py
│   ├── config.py
│   ├── core/
│   ├── storage/
│   ├── models/
│   ├── providers/
│   ├── collectors/
│   │   ├── crypto/
│   │   ├── equity/
│   │   ├── fund/
│   │   └── news/
│   └── adapters/
├── tests/
├── pyproject.toml
├── requirements.txt
└── Makefile
```

冻结原则：

1. `core/` 负责 fetcher/registry/key manager 等基础设施。
2. `storage/` 负责共享连接池、writer、batch。
3. `models/` 承载 candle/news 等标准数据模型。
4. `providers/` 承载 provider 适配层。
5. `collectors/` 承载按业务域组织的执行入口。
6. `adapters/` 只存放跨域复用适配器，不承载业务逻辑。

## 8. 配置兼容策略（冻结版）

在未切换默认语义前，配置策略遵循以下规则：

1. 旧环境变量继续保留可读能力。
2. 新环境变量只通过 `config/.env.example` 暴露，不要求立即修改 `config/.env`。
3. `collector-service` 必须支持兼容读取以下旧键：
   - `DATABASE_URL`
   - `MARKETS_SERVICE_DATABASE_URL`
   - `CRYPTO_WRITE_MODE`
   - `BACKFILL_MODE`
   - `BACKFILL_DAYS`
   - `BACKFILL_START_DATE`
   - 新闻 retention / timeout / failure cooldown 相关配置
4. 新键命名必须提供“旧键 -> 新键”的对照表。
5. 在 cleanup 阶段之前，不允许要求使用者删除旧键。

建议增加一个专门的配置对照表文档，至少包含：

1. 保留
2. 废弃但兼容
3. 改名
4. 新增

## 9. 基金链路专项收敛（最高优先级）

### 9.1 本阶段目标

在不移除现有 TUI 直连能力的前提下，先冻结基金链路的领域模型和迁移边界。

### 9.2 需要补齐的设计项

#### A. 基金读模型

必须明确 TUI 最终依赖哪些字段，而不是只定义原始采集表。至少包括：

1. `symbol`
2. `name`
3. `price`
4. `prev_close`
5. `open`
6. `high`
7. `low`
8. `volume`
9. `amount`
10. `ts`
11. `source`
12. freshness 判定字段

#### B. 曲线策略

必须单独定义：

1. live curve 从哪里来
2. 15D daily curve 从哪里来
3. 场外基金是否提供历史曲线
4. 历史曲线的缓存和过期策略

#### C. Symbol 规范

必须定义以下编码在不同层的统一规则：

1. `SH510300`
2. `SZ159915`
3. `024389`

至少要明确：

1. 采集层表示
2. 存储层主键
3. 查询层输入
4. TUI 展示层映射
5. 信号匹配层规则

#### D. 动态候选池闭环

必须明确：

1. 用户切领域时新增 symbol 谁负责纳入采集
2. 用户 `+/-` 自选后多久可见
3. 未采集到数据时 TUI 如何提示
4. 回退到直连抓取的条件是什么

#### E. 排名与 micro snapshot 归属

默认方案：

1. 排名与 micro snapshot 暂留 TUI
2. 底层数据源可逐步切换
3. 待基金链路稳定后再评估是否上移服务端

### 9.3 本阶段验收

至少覆盖以下样本：

1. `SH510300`
2. `SZ159915`
3. `024389`

至少验证以下能力：

1. quote 展示
2. 图表展示
3. 领域页切换
4. 自选新增和删除
5. signal 叠加
6. freshness 判断
7. 无数据回退

### 9.4 本阶段回滚

若任一验收项失败，则：

1. TUI 继续使用现有直连基金抓取逻辑
2. 新读模型只保留为实验入口
3. 不切默认基金数据源

## 10. collector 引入阶段（兼容优先）

### 10.1 本阶段目标

在不破坏现有 `data-service` / `markets-service` 入口的前提下，冻结 collector 的最小骨架和兼容配置加载策略。

### 10.2 本阶段只做

1. 不切默认根脚本语义

## 13. 启动脚本与入口策略

### 13.1 默认原则

在 cleanup 阶段前，根脚本现有入口全部保持不变：

1. `start`
2. `stop`
3. `status`
4. `restart`
5. `run`

### 13.2 新入口暴露原则

若需要引入 collector 入口，应满足：

1. 先以显式新命令暴露
2. 不覆盖现有默认命令
3. 相关逻辑同步补到 `scripts/init.sh`、`scripts/check_env.sh`、必要时补到 `scripts/verify.sh`

### 13.3 禁止事项

1. 禁止只改 `scripts/start.sh` 而不补其他顶层脚本
2. 禁止在未完成灰度前切换根脚本默认服务拓扑

---

## 14. 灰度与双跑策略

所有高风险切换都必须支持双跑。

最低要求如下：

1. 新旧采集链并行运行一段稳定窗口
2. 对账口径提前定义
3. 明确切默认的 gate
4. 明确回退触发条件

建议的最小对账维度：

1. 采集是否成功
2. 数据 freshness
3. TUI 是否有可展示数据
4. 基金页核心交互是否退化
5. 关键 CLI 是否仍可启动

---

## 15. 回滚策略

### 15.1 通用回滚原则

任何阶段只允许做“局部可回退”的改动，不允许把多个高风险动作绑在同一批次。

### 15.2 基金链路回滚

若 DB 读失败、数据为空、图表退化或 freshness 不达标，则：

1. TUI 回退到现有直连抓取
2. 不移除 `quote.py` 里的现有基金抓取路径
3. 读库逻辑保留为实验开关

### 15.3 collector 回滚

若 collector 新入口影响现有命令或配置兼容，则：

1. 关闭新入口暴露
2. 保留代码但停止接线
3. 继续使用旧服务路径

### 15.4 cleanup 回滚

cleanup 阶段如遇回归，直接停止 cleanup，不做目录迁移或命令默认切换。

## 16. 验收口径

每个阶段都至少要给出“命令 + 预期结果”。

建议作为阶段性硬验收的稳定入口：

1. `./scripts/init.sh`
2. `./scripts/check_env.sh`
3. `./scripts/start.sh status`
4. `./scripts/start.sh run`
5. `python scripts/tradecat_get_quotes.py NVDA`
6. `python scripts/tradecat_get_signals.py --symbol BTCUSDT --timeframe 1m --limit 5`
7. `python scripts/tradecat_get_news.py --symbol BTCUSDT --limit 5 --since-minutes 120`

基金专项还应补人工验收清单：

1. 基金页启动后能展示样本标的
2. 图表不空白
3. 自选操作可见
4. 信号叠加不报错
5. 数据缺失时有明确回退或降级行为

## 17. 推荐的执行拆分

将原来的“大一统服务合并”拆成三个独立计划。

### Plan A: 基金链路抽离

目标：

1. 只收敛基金读模型、symbol 规范、曲线策略、回退逻辑
2. 不默认引入 schema 变更
3. 不切 TUI 默认数据源

### Plan B: collector 兼容引入

目标：

1. 冻结 collector 目录和配置契约
2. 引入兼容入口
3. 分片迁移共享存储和业务采集能力

### Plan C: cleanup 与默认切换

目标：

1. 仅在前两者稳定后执行
2. 包含 `_deprecated/`、文档更新、命令默认切换
3. 必须最后做
